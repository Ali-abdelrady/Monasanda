# API guide

This guide describes the HTTP API currently implemented by the backend.

## Connection and authentication

- Local base URL: `http://localhost:8080`
- All routes are under `/api`.
- Send and accept JSON (`Content-Type: application/json`).
- Login is the only public endpoint. The profile, vacation-batch, and attendance endpoints require the `session_id` cookie.
- Login sets an HTTP-only `session_id` cookie that expires after 30 minutes. Browser clients should send requests with credentials enabled (for example, `credentials: "include"` with `fetch`). JavaScript cannot read the cookie; the browser sends it automatically.
- The server currently does not configure CORS. For a separate frontend development server, use a same-origin development proxy or configure CORS on the backend.
- There is no logout endpoint.

Successful responses include `"hasError": false`. Error response bodies are generated by the backend error helper; clients should also check the HTTP status and should not assume a particular error-body schema.

## Endpoints

| Method | Path | Auth required | Description |
|---|---|---:|---|
| `POST` | `/api/login` | No | Sign in and set the session cookie |
| `GET` | `/api/me` | Yes | Get the signed-in user's profile |
| `GET` | `/api/vacation-batches` | Yes | List vacation batches |
| `POST` | `/api/vacation-batches` | Yes | Create a vacation batch |
| `GET` | `/api/vacation-batches/{id}` | Yes | Get one vacation batch |
| `PUT` | `/api/vacation-batches/{id}` | Yes | Replace editable vacation-batch fields |
| `DELETE` | `/api/vacation-batches/{id}` | Yes | Delete a vacation batch |
| `GET` | `/api/attendances` | Yes | List attendance records |
| `POST` | `/api/attendances` | Yes | Create an attendance record |
| `GET` | `/api/attendances/{id}` | Yes | Get one attendance record |
| `PUT` | `/api/attendances/{id}` | Yes | Replace an attendance record's editable fields |
| `DELETE` | `/api/attendances/{id}` | Yes | Delete an attendance record |

IDs in paths must be positive integers. List endpoints currently return all records; filtering, sorting, and pagination are not implemented.

## Login

`POST /api/login`

Request:

```json
{
  "email": "user@example.com",
  "password": "your-password"
}
```

Success response:

```json
{
  "hasError": false
}
```

The response also sets the `session_id` cookie. Email is required by request validation. Invalid credentials return an error response.

## Current user

`GET /api/me` requires a valid session cookie and returns the signed-in user's public profile:

```json
{
  "hasError": false,
  "user": {
    "id": 2,
    "email": "user@example.com"
  }
}
```

Expired sessions are rejected immediately by protected endpoints. The backend also deletes expired session rows in the background at startup and every 15 minutes.

## Vacation batches

Create and update requests use this shape:

```json
{
  "name": "Summer leave",
  "startDate": "2026-07-01T00:00:00Z",
  "endDate": "2026-07-14T23:59:59Z"
}
```

`name` is required. Dates use JSON timestamps (RFC 3339). Send both dates when creating or updating. `createdBy`, `createdAt`, and `updatedAt` are server-managed; do not send them.

Batch response object:

```json
{
  "id": 1,
  "name": "Summer leave",
  "startDate": "2026-07-01T00:00:00Z",
  "endDate": "2026-07-14T23:59:59Z",
  "createdBy": 2,
  "createdAt": "2026-06-01T10:00:00Z",
  "updatedAt": "2026-06-01T10:00:00Z"
}
```

A single-batch response has `hasError` and `vacationBatch` keys. The list response has `hasError` and `vacationBatches` keys; `vacationBatches` is an array of the batch objects shown above.

Delete returns:

```json
{ "hasError": false }
```

## Attendance

Create and update requests use these fields:

```json
{
  "batchId": 1,
  "name": "Alex Example",
  "location": "North gate",
  "phoneNumber": "5551234567",
  "militaryNumber": "ABC123",
  "status": "present",
  "notes": "Arrived on time",
  "startDate": "2026-07-01T00:00:00Z",
  "endDate": "2026-07-14T23:59:59Z"
}
```

| Field | Type | Required / constraints |
|---|---|---|
| `batchId` | integer | Required; positive |
| `name` | string or `null` | Optional |
| `location` | string or `null` | Optional |
| `phoneNumber` | string or `null` | Optional; maximum 12 characters |
| `militaryNumber` | string or `null` | Optional; maximum 13 characters |
| `status` | string | `"present"` or `"absent"`; defaults to `"absent"` if omitted |
| `notes` | string or `null` | Optional |
| `startDate` | timestamp or `null` | Optional |
| `endDate` | timestamp or `null` | Optional; cannot be earlier than `startDate` |

Attendance response objects additionally include server-managed fields:

```json
{
  "id": 10,
  "batchId": 1,
  "name": "Alex Example",
  "location": "North gate",
  "phoneNumber": "5551234567",
  "militaryNumber": "ABC123",
  "status": "present",
  "notes": "Arrived on time",
  "startDate": "2026-07-01T00:00:00Z",
  "endDate": "2026-07-14T23:59:59Z",
  "checkedInAt": "2026-06-01T10:00:00Z",
  "checkedInBy": {
    "id": 2,
    "email": "user@example.com"
  },
  "createdBy": 2,
  "createdAt": "2026-06-01T10:00:00Z",
  "updatedAt": "2026-06-01T10:00:00Z"
}
```

Optional attendance fields may be `null` in responses. When a record is present, `checkedInBy` is the user object (`id` and `email`) for the person who checked in; it is `null` while absent. On create/update, the backend sets `createdBy` to the signed-in user. If status is `"present"`, it sets `checkedInAt` to the current time and records that user's ID in the database; for `"absent"`, check-in details are cleared. Do not send these server-managed fields.

Successful response envelopes use `attendance` for a single record and `attendances` for the list. Delete returns `{ "hasError": false }`.

## Frontend integration notes

- Use `credentials: "include"` for browser requests so the session cookie is sent.
- `PUT` requests should include all editable fields, not just changed fields.
- A missing record, invalid ID, invalid payload, or expired session returns an error; handle non-2xx responses in the UI.
